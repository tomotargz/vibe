# プロセス変更履歴

## 2026-09-27 初版
- インタビューで開発プロセスを決定した(MVP→反復、TDD、機能ブランチ+PR、ステップごとの確認、Markdownでのバックログ管理、Lint・Format・CI、セルフレビュー後にユーザーがレビュー)
- プロセスの見直しは、初期は1機能完了ごとに行う

## 2026-09-27 見直し1回目
KPTで振り返り、以下を【お試し運用】として採用した。
- バックログの更新は作業のPRの中で行う。理由: マージ後に更新するとmainへの直接コミットか、更新だけのPRが必要になるため
- バックログにない作業は、始める前にバックログへ追加する。理由: 初回の作業がバックログになく、完了として記録できなかったため
- ユーザーが複数のステップをまとめて指示したら、その範囲を承認済みとして扱う。理由: まとめて指示された場合の確認の要否があいまいだったため
- ドキュメントだけの変更ではテストと実装の手順を省略する。ただしセルフレビューはできる限り行う。理由: 今のフローがドキュメントだけの変更に合わず、手順を黙って飛ばしていたため

## 2026-09-27 見直し2回目
- 1回目の【お試し運用】4件は、効果があったので正式に採用した(バックログの更新をPRの中で行う、着手前にバックログへ登録する、まとめて指示された範囲は承認済みとして扱う、ドキュメントだけの変更は手順を省略しセルフレビューは行う)
- 定期の見直しを1機能ごとから3機能ごとに変えた。理由: 見直しのたびにブランチとPRが1組増え、負担が大きいため
- Claudeが違和感を覚えたら、その場で `docs/process-notes.md` に書く【お試し運用】。理由: メモが空のままで、見直しの材料を記憶から集めていたため
- PRを出すときにClaudeが次の項目を予告し、異議なくマージされたら着手の確認済みとして扱う【お試し運用】。理由: 着手の確認が暗黙になっていたため、ルールとして明文化する
- 「見直しを作業と同じPRに入れる」案は採用しなかった(3機能ごとにしたことで負担は十分に減るため)

## 2026-09-27 PRの説明のルールを追加(ユーザーの指摘による臨時の変更)
- PRの説明には変更内容だけを書く。理由: 次のタスクの予告をPRの説明に書いていたが、変更内容と関係がないため
- 次の項目の予告は、PRの説明ではなくチャットで行う

## 2026-09-27 TDDのサイクルを明記(ユーザーの指摘による臨時の変更)
- 手順を レッド → グリーン → リファクタリング に分け、テストケースごとに繰り返す形にした。理由: 「実装し、リファクタリングする」が1つの手順にまとまっていたため、グリーンの後のリファクタリングが抜けていた
- リファクタリングの手順で改善点がなければ、「なし」とその理由を報告する。理由: リファクタリングを黙って飛ばさないようにするため
- `go vet`・`gofmt`・`go test` はサイクルごとに実行する。`/code-review` は機能全体で1回にする。理由: 機械的なチェックは軽いので毎回行い、差分全体を読むレビューは毎回だと重複が多いため
